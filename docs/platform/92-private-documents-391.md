# #391 — Private Supabase-managed Files & Docs (staged release)

**Prepared November 18, 2026 (US Eastern).** This batch depends on **PR #132 / #390** and is intentionally held behind an **unapplied database migration**. There is no working cloud storage until the migration is reviewed and deployed to an isolated environment, with a separate approval for production. Do **not** imply uploaded files are available on the current live app.

## User experience implemented

- **Tools → Files & Docs → Library** combines existing browser-only links and signed-in Supabase-managed documents, shows verified byte sizes, owner Company/Deal associations, searchable folder labels, size/date/provider sorting, and per-provider known-size counts.
- **Upload a document** is available to CRM editors in a cloud workspace only after private storage is activated. Target: a currently visible **Company or Deal**. One selected file at a time (up to 15 MiB) and an optional virtual folder path. Accepted extensions: PDF, PNG/JPEG/WebP, TXT/CSV, Word, Excel, PowerPoint. No HTML, executables, or inline preview.
- **Company/Deal → Files & Docs** includes the same stored documents and upload control alongside existing local external links. No stored Quote or external-Quote files in #391.
- **Download** is by authenticated Storage API as a browser Blob, not a persisted/public signed URL.
- **Trash / Restore / Permanently delete** are guarded mutation actions; trash hides the file from the active library but still counts towards bytes, and permanent deletion removes object bytes before deleting metadata. A partially completed upload stays **pending** so it can be retried or intentionally deleted.
- The library displays **managed storage allowance** (500 MiB per org) distinct from indexed usable bytes and separately labeled from provider billing. New pending uploads reserve 15 MiB until finished; trash retains its actual bytes. Quotas are fixed safety ceilings for this first slice, not customer-configurable yet.
- The existing #390 BYO provider model remains. This batch does not add BYO Supabase, S3/R2 or OAuth connectors; those remain separate integrations.

## Trust and storage model

1. Browser inserts a pending `public.crm_file_objects` row; database RLS checks logged-in organization, permitted CRM area, and an existing Company/Deal in that same organization. The object key is generated by PostgreSQL: `{organization_uuid}/{random_file_uuid}`; the client cannot move an object to another organization.
2. Browser uploads to **private** bucket `sales-documents` using the signed-in Supabase session, never a service-role key. The `storage.objects` INSERT policy requires a matching pending metadata row owned by that user. Upsert and overwrite are blocked.
3. Browser updates the file state pending → ready. A restricted database trigger validates that the actual object exists and checks the **Storage-reported byte size and MIME type** before publishing it in the library. Browser size fields are never accepted as storage accounting.
4. Both the document metadata SELECT policy and the private Storage object SELECT policy require visibility of the underlying Company/Deal under its own RLS, in addition to organization membership. CRM-area editors can manage trashed/pending files **only while that underlying record remains visible**. A deleted or otherwise inaccessible target is not an authorization bypass.
5. A database lock serializes file reservations within each organization, conservatively counting pending as 15 MiB and counting trashed bytes against the 500 MiB cap. This is an **application safety allowance**, not a Supabase invoice/quota report. Actual billed usage may also include overhead and other buckets.
6. Never expose any private Storage URL as public, store signed URLs in browser state, store cross-org credentials or assume BYO-Supabase RLS will understand a SalesShop JWT.

## November 19 follow-up — generated-column and orphan fixes

- **Confirmed PostgreSQL 17 issue:** a stored generated column on `NEW` cannot be accessed from a BEFORE trigger. The staged finalize trigger now constructs the Storage path from immutable `organization_id` and `id` rather than accessing `NEW.object_path`. The regression test specifically rejects this mistake. See https://www.postgresql.org/docs/17/trigger-definition.html.
- **Orphan safety:** the previous editor-bypass approach was removed during the follow-up security review. Files linked to deleted or inaccessible records do not appear in the normal library. An explicit admin-only maintenance/reconciliation mechanism will be required to reclaim orphan bytes without exposing hidden records.
- **Strengthened staging matrix:** a working positive control from org B ensures the cross-tenant test actually uses two authorized organizations. Added anonymous-download denials, duplicate path overwrite denial, immutable target/organization/uploader tests, and SQL deletion ordering checks.
- **Read-only live schema preflight:** verified both existing private CRM permission functions, the three bucket constraint columns, three Storage object metadata columns and four team membership columns. No live schema or Storage object was modified.
- **Release remains gated:** neither the staged SQL nor actual uploads have been deployed; true staging Auth/RLS and TypeScript/Cloudflare/browser checks remain outstanding.

## November 19 — Record-visibility parity audit

A read-only inspection of the *live* schema found that Companies and Deals currently have organization-member SELECT RLS, while Quotes have separate private-grant checks. Because record visibility may become configurable, it is not enough for `storage.objects` to check membership only: its SELECT and INSERT policies now additionally check visibility/existence of the linked Company or Deal through the source table's RLS. The file index's SELECT policy has the same bound. A CRM editor's right to edit the organization is **not** a substitute for permission to see a particular record. The former orphan-visibility editor fallback has been removed. A privileged cleanup workflow with audited authorization is required before deleted-target bytes can be reclaimed.

**Remaining release blockers:** Run TypeScript/Vitest/build, execute two-organization permission tests in an isolated environment, verify invalid MIME and bucket limits against real Storage, and design a secure maintenance path for file objects left after their source records are deleted. Do not deploy SQL or enable live uploads yet.

## November 19 — Least-privilege file writes and orphan inventory

- The staged `crm_file_objects` table now grants `INSERT` only for record-link metadata, leaving UUID, uploader, size, initial status and audit fields **server-generated**. Authenticated clients can `UPDATE` only the lifecycle `status` column, with transitions still guarded by the database trigger and RLS.
- Metadata and private object reads both require the same underlying CRM record visibility, not merely organization membership or editor role.
- The Files & Docs UI reports **visible managed bytes/reservations**, not a misleading exact organization-wide remaining allowance from RLS-filtered rows. The 500 MiB upload cap remains enforced in the database trigger across all organization files, including pending and trashed entries.
- `docs/platform/sql/391-orphan-audit-staging.sql` contains a **read-only, database-operator-only** report of missing linked CRM targets, pending-upload reservations, deleted-object discrepancies and soft-deleted bytes. It exposes no customer-facing RPC, requires visibility across all records to classify actual missing targets, and cannot delete or reclaim bytes.
- Revocation or removal of the underlying record may make its files invisible through normal RLS. A separately authorized maintenance process and retention policy are **release blockers** before full multi-tenant production enablement; hiding orphan files is deliberate, not a completed cleanup solution.
